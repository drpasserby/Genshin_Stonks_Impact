# 价格机制与因子模型（PRICING）

> 本文说明**本系统里价格是怎么动起来的**：数据模型、每一次结算的完整流程、
> 全部影响价格的因子与公式、基金与角色的双向联动、可调参数、以及对应的代码位置。
>
> 适用版本：一期指数基金（2026-09）。阅读顺序建议：先看第 2 章（一次结算做了什么），
> 再看第 3/4 章（两个定价公式），最后按需查参数表与代码索引。

---

## 1. 总览：一切都发生在「周期结算」里

系统**不是**逐笔成交即时改价，而是**周期性批量结算**：

```
每 cycle_minutes 分钟（默认 10，可在 root 控制面板在线调整）
  ↓
P1 撮合  把可成交的限价挂单按「当前价」成交
P2 统计  统计这一窗口内每只标的的买入量/卖出量
P3 定价  用因子模型算出新价格，落一根周期 K 线
P4 收盘  每日 15:00 生成日 K 并重置日行情字段
```

**关键设计**：所有价格联动（包括基金）都只在 P3 里算一次，**绝不在成交瞬间传播**。
这样下单路径永远是「写 orders → 可能写 trades/holdings」这几条固定 SQL，
不管后面挂着多少基金、基金里有多少成分股，下单开销都**不变**。

## 2. 数据模型

### 2.1 角色股票与指数基金共用一张表

```sql
stocks
  id, code, name
  type        ENUM('STOCK','FUND')   -- 角色股 / 指数基金
  avatar_url, price, prev_close, open, high, low, volume, total_shares
  nav         DECIMAL(14,4) NULL     -- 仅基金：最近一次结算算出的单位净值

fund_constituents
  fund_id        → stocks.id (type=FUND)
  constituent_id → stocks.id (一期仅 type=STOCK)
  weight         DECIMAL(8,4)        -- 相对权重，内部会归一化
  UNIQUE(fund_id, constituent_id)
```

**为什么基金不单独建表**：`orders / trades / holdings / watchlists / price_history /
news_stocks / votes` 全部通过 `stock_id` 关联。基金作为 `stocks` 的一行后，
「下单、撮合、冻结、清算、持仓盈亏、K 线、盘口、新闻、投票、自选」**全部零改动复用**。
如果另建一张 `funds` 表，上述每一项都要写第二套代码路径。

### 2.2 关键约束

| 约束 | 说明 |
|---|---|
| `stocks.code` / `stocks.name` 唯一 | 基金名也占用同一个命名空间 |
| `price_history (stock_id, period, ts)` 唯一 | 周期线与日线共用表；`period` 是 `VARCHAR(8)`（`10m`/`2m`/`1d`），**不是 ENUM**，因为撮合周期可在线调整 |
| 基金份额固定 | 一期为「封闭式」，不做申购赎回，买卖只影响价格 |

## 3. 角色股定价公式（STOCK）

### 3.1 公式

```
涨跌幅 = clamp( (wP×压力 + wN×新闻 + wV×投票 + wS×市场情绪 + wI×基金传导)
                × 基础波动率 , ±单周期限幅 )

压力      = clamp( 净买入 / 总股本 × 压力灵敏度 )
新闻      = clamp( 该标的全部有效新闻影响分的平均 )
投票      = clamp( 该标的股票级投票的方向均值 × 倍率均值 )
市场情绪  = clamp( 该标的全部有效市场情绪影响分的平均 )                      ← 2026-09-14 新增
基金传导  = clamp( Σ_关联基金 ( 该基金压力 × 本角色在该基金中的权重占比 ) )    ← 一期新增
```

默认权重：`wP=0.5`、`wN=0.3`、`wV=0.2`、`wS=0.2`、`wI=0.25`（`wS`/`wI` 可在面板调）。
基础波动率默认 `0.02`，单周期限幅默认 `±10%`。

> 权重和 = 1.45 > 1 是**有意为之**，不是 bug：各因子互相独立、可同时打满，
> 全部打满时正好触到 ±10% 限幅（1.45 × 0.02 = 2.9% < 10%，其实仍到不了限幅）。
> 限幅真正拦的是「压力打满 + 情绪打满 + 传导打满」叠加极端行情的尾部。

### 3.2 逐项解释

**① 压力因子（用户买卖）**

净买入 = 本周期买入量 − 卖出量（买卖双边各计一次）。除以总股本再乘灵敏度，
得到「买卖力量相对流通盘的强度」，限幅到 ±1。

> 例：流通股 500 万、灵敏度 200，净买入 2.5 万股 → 压力 = 2.5万/500万×200 = 1.0（打满）。

**② 新闻因子**

每条有效新闻的影响分 = `方向(±1) × 强度(0~100)/100 × 投票平均倍率`，再对所有有效新闻取平均。

- 有效期：发布时按「当时的周期数 × 撮合周期」写死 `expiresAt`，过期自动不计入
- 一条新闻若无人投票，倍率按 1 计算（即"作者设定的方向与强度全额生效"）
- 有人投票时，投票方向会**覆盖**作者方向，倍率取平均
- **只认 `reviewStatus='APPROVED'`**：待审新闻绝不影响股价

**③ 投票因子**

操作员对该标的的看涨/看跌投票：`方向均值(±1) × 倍率均值(0.5~2.0)`，限幅 ±1。
投票有窗口（默认最近 `news_ttl_cycles` 个周期内有效），防止陈年投票长期生效。

**④ 市场情绪因子（2026-09-14 新增）**

社交平台（当前是 NGA）自动抓取 + AI 总结出来的情绪快照，**独立成一档**，不并进新闻因子：

| 维度 | 新闻因子 | 市场情绪因子 |
| --- | --- | --- |
| 来源 | 人工发布的新闻引用 | 脚本自动抓取的社区讨论 |
| 影响分 | `方向 × 强度/100 × 投票倍率` | `方向 × 强度/100`（情绪没有投票） |
| 多条聚合 | 取平均后 clamp | 取平均后 clamp（口径完全一致，所以可以直接相加、可以横向比权重） |
| 有效期 | `news_ttl_cycles` 个撮合周期（发布时写死过期时间） | `sentiment_decay_hours` 小时（默认 72，从抓取时刻起算） |
| 审核 | 必须 APPROVED | 由 `sentiment_before_review` 开关决定（默认**待审也生效**） |

为什么分开算而不是合并进新闻：两者数据来源、更新频率、审核口径都不同；
分开以后要单独调权（`wS`）、单独关停（置 0）、单独排查（日志里 `情绪x.xxxx`）都干净。

为什么时效用「小时」而不是「周期数」：情绪快照更新更频繁，用固定小时数更好理解，
也不会被「撮合周期」改动连带影响（改周期不会让情绪突然过期或永不过期）。

> 单周期价格影响 ≈ `wS × 情绪因子 × 基础波动率`：默认 `0.2 × 1.0 × 0.02 = ±0.4%`（满情绪）。

**⑤ 基金传导因子（一期新增）**

```
for 每个本周期有净买卖压力的基金 F:
    for 每个成分股 S in F:
        传导[S] += 压力(F) × 权重(S in F) / Σ权重(F)
传导[S] = clamp(传导[S], ±1)
```

含义：**买基金 = 按权重替它所有的成分股下单**。
基金压力打满、3 只等权成分股时，每只成分股拿到 `1 × 1/3 = 0.3333` 的传导、
贡献涨跌幅 `0.25 × 0.3333 × 0.02 ≈ 0.167%`。

> 若某周期所有基金都没有净买卖，这段计算**整段跳过**（`pressure=0` 直接 continue）。

### 3.3 计算结果落库

```
price   = 旧价 × (1 + 涨跌幅)
high    = max(今日高, 新价)
low     = min(今日低, 新价)
K线      = (开=旧价, 高/低=两者极值, 收=新价, 量=买量+卖量)
```

## 4. 指数基金定价公式（FUND）

基金**不套用**角色股公式，而是「向净值收敛」：

```
① 净值 NAV = Σ(权重ᵢ × 成分股本轮新价ᵢ) / Σ权重ᵢ

② 情绪 = clamp( 自身压力 + (新闻×wN + 投票×wV + 市场情绪×wS) / wP )
③ 溢价 = clamp( 情绪 × 基金溢价系数 , ±0.3 )
④ 目标价 = NAV × (1 + 溢价)
⑤ 涨跌幅 = clamp( (目标价 / 当前价 − 1) × 跟踪速度 , ±单周期限幅 )
```

默认：溢价系数 `0.05`、跟踪速度 `0.5`。

> ②为什么三档都先除以 `wP`：这一步是**量纲归一**，把「新闻/投票/情绪」折算成
> 「压力等价」——`wN/wP = 0.6`，即「一条满强度新闻 ≈ 压力 0.6」。
> 2026-09-14 加入情绪后同样按 `wS/wP = 0.4` 折算（满情绪 ≈ 压力 0.4），
> 所以基金不需要第二套权重表，改 `wS` 会自动同时影响角色股与基金，口径永远一致。

> **⚠️ 上市初始价必须等于净值（2026-09-12 起强制）**
> 基金价格朝净值收敛，所以「初始价 ≠ 净值」等价于**给先发现的人送一段确定性套利**：
> 每周期最多 ±10%，20 个周期就能把 6 倍差距吃干净。
> 真实事故：FUND003 按 140 上市而净值 887 → 连续 20 轮每轮 +10% → 5 个账号无风险拿走约 170 万摩拉。
> 因此**新建基金不允许手填价格**：必须先选成分股，服务端按当时加权净值定价
> （`GET /admin/fund-rules` 提供数量限制；改成分股后也会立即把价格对齐到新净值）。
> 参数换算：`(NAV/价格 − 1) × 0.5` 超过 ±10% 时每轮走满限幅，
> 收敛所需轮数 ≈ `log(NAV/价格) / log(1.1)`。

### 4.1 怎么理解这四步

- **①②③**：基金也有自己的新闻与投票（一期要求），它们和自身买卖压力一起，
  表达为「相对净值的**溢价/折价**」。新闻过期、压力消失后溢价自动归零。
- **④⑤**：价格朝目标价走 **一半**（跟踪速度 0.5）。这是标准的**一阶滞后滤波**：

```
误差ₙ₊₁ = 误差ₙ × (1 − 跟踪速度)
```

因为 `|1 − k| < 1`（k ∈ (0,1]），**无论目标价怎么跳，价格必然收敛，不会震荡或发散**。
这正是选它而不是「解联立方程」的原因。

### 4.2 三个方向的联动

| 方向 | 机制 | 成本 |
|---|---|---|
| **成分股 → 基金** | 成分股价格变 → NAV 变 → 基金价格被拉过去 | **零额外计算**（NAV 是内存里用本轮新价算出来的，不查库、不落库） |
| **基金 → 成分股** | 基金压力 → 第 3.2④ 的传导因子 → 成分股涨跌幅 | 内存里一次加权求和，O(基金数 × 成分数) |
| **基金 → 基金** | 一期**不支持**（管理员配成分时会被拒绝） | — |

### 4.3 会不会互相推动到失控？

不会，有三重保险：

1. **传导与压力都限幅 ±1**，且只按权重分摊（基金压力打满，3 个成分股各分到 1/3）；
2. **基金价格是收敛而非外推**，误差每轮衰减一半；
3. **溢价只由当期情绪决定、不累计**——玩家停手，下一轮溢价归零，价格回落净值。

玩家买基金 → 基金涨（溢价，短期、会衰减）+ 成分股涨（传导，**永久性价格台阶**）→
NAV 抬高 → 基金价格再跟着上一个台阶。所以长期看，**基金的涨幅终究来自成分股涨幅**，
这与真实指数基金的逻辑一致。

### 4.4 数值示例（默认参数）

3 只等权成分股（各 1000 价）+ 1 只基金（1000 价），玩家把基金压力买满：

| 对象 | 结果 | 推导 |
|---|---|---|
| 每只成分股 | 1000 → **1001.6667**（+0.1667%） | 传导 1×(1/3)=0.3333 × wI 0.25 × 0.02 |
| 基金 NAV | **1001.6667** | 成分股等权平均 |
| 基金溢价 | **5%** | 压力 1 × 溢价系数 0.05 |
| 基金价格 | 1000 → **1025.875**（+2.5875%） | (1001.6667×1.05 / 1000 − 1) × 0.5 |

## 5. 一次结算的完整执行顺序（代码视角）

```
tick()                                   jobs/cycleJob.js
 ├─ refreshRuntime()                      刷新运行时配置（面板改的参数立即生效）
 ├─ isTradingOpen()？ 是 → settleAll()     P1 撮合（services/tradingService.js）
 ├─ collectCycleStats(prev, now)          P2 统计 → Map<stockId,{buyVol,sellVol}>
 └─ recomputeAll(stats)                   P3 定价（见下）
     ├─ Stock.findAll()                    一次读全部标的
     ├─ loadFactorsBatch(ids)              4 条 SQL 取全部新闻/投票因子
     ├─ 逐标的算压力 computePressureFactor
     ├─ loadFundGraph()                    基金成分图（内存缓存 60s，改动即失效）
     ├─ buildInfluenceMap(...)             基金压力 → 成分股传导
     ├─ for 角色股: computePrice(...)        ★ 用「本轮基金压力」做传导
     └─ for 基金:   computeFundPrice(...)    ★ 用「角色股本轮新价」算 NAV
     └─ 单事务批量落库                      1 条批量 K 线 + N 条 UPDATE
```

**为什么这样排序就一定无环**：
成分股的传导因子只依赖基金的**成交量压力**（不依赖价格），
基金的价格只依赖**已算完的成分股价格**。
所以「先角色、后基金」一趟走完即可，不需要拓扑排序、也不需要把联动延迟到下一轮。

## 6. 全部可调参数（root 控制面板 → 系统开关与参数）

> 面板左侧 TAB 顺序 = `SETTING_SCHEMA` 顺序；「市场情绪 · 运行状态」会自动并进「市场情绪」组。
> 情绪定价的 3 个开关/权重都在**「📡 市场情绪」**组里（与抓取参数、Gemini 参数同组）。

| 分组 | 键 | 类型 | 默认 | 作用 |
|---|---|---|---|---|
| 交易控制 | `base_volatility` | number | 0.02 | 基础波动率（每周期涨跌幅的放大幅度） |
| 交易控制 | `max_change` | number | 0.1 | 单周期涨跌幅上限 |
| 交易控制 | `cycle_minutes` | number | 10 | 撮合周期；**K 线档位随之变为 `Nm`** |
| 新闻与投票 | `news_ttl_cycles` | number | 6 | 新闻有效周期数（同时决定投票统计窗口） |
| **市场情绪** | `sentiment_before_review` | bool | 1 | **审核通过前是否影响股价**（开=待审也生效；关=必须 APPROVED；已驳回永不生效） |
| **市场情绪** | `sentiment_weight` | number | 0.2 | 情绪因子权重 wS（0 = 情绪只展示不影响股价） |
| **市场情绪** | `sentiment_decay_hours` | number | 72 | 一条市场情绪影响股价多久（小时，从抓取时刻起算） |
| **指数基金** | `fund_enabled` | bool | 1 | 基金机制总开关（关掉则基金按普通股定价） |
| **指数基金** | `fund_influence_weight` | number | **0.25** | 基金 → 角色 传导权重 |
| **指数基金** | `fund_tracking_rate` | number | 0.5 | 基金向净值收敛速度 |
| **指数基金** | `fund_premium_gain` | number | 0.05 | 基金压力 → 溢价系数 |
| **指数基金** | `fund_min_constituents` | number | 3 | 基金最少成分股 |
| **指数基金** | `fund_max_constituents` | number | 15 | 基金最多成分股 |

以下仍在 `.env`（不常改，属于「公式权重」层；面板里的 `sentiment_weight` 会覆盖它）：

| 变量 | 默认 | 作用 |
|---|---|---|
| `WEIGHT_PRESSURE` | 0.5 | 压力因子权重 wP |
| `WEIGHT_NEWS` | 0.3 | 新闻因子权重 wN（基金的新闻溢价也用它） |
| `WEIGHT_VOTE` | 0.2 | 投票因子权重 wV（同上） |
| `WEIGHT_SENTIMENT` | 0.2 | 情绪因子权重 wS 的 .env 兜底（面板值优先） |
| `PRESSURE_GAIN` | 200 | 压力灵敏度 |
| `DAILY_CLOSE_HOUR` | 15 | 每日收盘生成日 K 的时点 |
| `ORDER_MIN_QTY` / `ORDER_MAX_QTY` | 1 / 1000000 | 单笔数量范围 |

### 调参速查

| 想要的效果 | 调什么 |
|---|---|
| 买基金更能拉动成分股 | ↑ `fund_influence_weight`（0.25 → 0.5 效果翻倍） |
| 基金更紧跟成分股 | ↑ `fund_tracking_rate`（→1 则一个周期完全对齐净值） |
| 基金自身买卖更能影响基金价 | ↑ `fund_premium_gain` |
| 行情太平淡 / 太疯 | `base_volatility`、`max_change` 同向调 |
| 想让行情更活跃 | ↓ `cycle_minutes`（注意 K 线档位会变） |
| 社区情绪影响太强 / 太弱 | `sentiment_weight`（0 = 只展示不影响；0.2 满情绪≈±0.4%/周期） |
| 不想让「未审核」的情绪影响股价 | `sentiment_before_review` 关（改为与新闻同口径） |
| 情绪影响时间太长 | ↓ `sentiment_decay_hours`（72 → 24 则只认最近一天的情绪） |

## 8. 性能设计（为什么这样最省服务器）

| 优化 | 收益 |
|---|---|
| **只在结算时联动，成交路径零传播** | 买 1 笔基金不会触发 N 个成分股写库；下单延迟与 DB 压力与基金数量无关 |
| **单事务批量落库** | 原来 157 个标的 = 157 个事务 + 157 次提交；现在 **1 个事务**，K 线用一条多行 `INSERT ... ON DUPLICATE KEY UPDATE` |
| **因子批量取数** | 原来每标的 4 条 SQL（127 只 = 508 条）；现在 **5~6 条**（多 1~2 条查市场情绪关联与情绪行） |
| **NAV 只在内存算，不落库两次** | 只有基金行的一次 UPDATE 带 `nav` 字段 |
| **成分图内存缓存 60s + 改动即失效** | 多数结算轮次 0 条关联查询 |
| **无活动即跳过** | 没基金买卖的周期，传导计算整段跳过 |
| **顺序无关、无需迭代求解** | 一趟 O(标的数 + 关联数) 扫完，200 标的 × 8 成分 ≈ 1600 次乘法（<1ms） |

> 估算：加 30 只基金后，每 10 分钟一轮的额外开销 ≈ 1ms CPU + 几十行 SQL。

## 9. 一期限制与后续规划

**一期已实现**
- 基金作为 `stocks.type='FUND'`，复用全部交易能力
- 封闭式固定份额；3~15 个成分股（可配）；权重相对值自动归一化

## 9. 单标的停牌与退市（stocks.status）

除了全局开关 `trading_enabled`，每个标的还有自己的状态 `stocks.status`：

| 值 | 含义 | 能否下单 | 是否参与撮合 | 价格 | 行情列表 | 持仓估值 |
|---|---|---|---|---|---|---|
| 1 | 正常 | ✅ | ✅ | 正常计算 | 显示 | 按现价 |
| 0 | **暂停交易（停牌）** | ❌ 拒绝并提示「停牌中」 | ❌ 跳过 | **仍随新闻/投票波动**（无买卖压力） | 显示并带「停牌」标记 | 按现价 |
| 2 | **已退市** | ❌ 拒绝并提示「已退市」 | ❌ 跳过 | **冻结**（不参与结算、不落 K 线） | 隐藏（详情页仍可访问并提示） | 按退市前最后价格保留 |

### 退市时的自动处理

退市会在**同一个事务**里顺带完成「撤销该标的全部未成交挂单」：

```
① 买单：解冻 reserved_amount → 退回用户 frozen_mora
② 卖单：解冻 holding.frozen_quantity
③ 挂单状态置为 CANCELLED
```

这样不会出现「挂单永远无法成交、资金被永久冻结」的僵局。撤单本身在停牌/退市期间**仍然允许**（让用户能主动退出）。

### 与基金的关系

- 退市的成分股不参与 `NAV` 计算（`recomputeAll` 直接过滤掉 status=2 的标的），
  因此基金净值不会因为一只退市股而异常
- 基金自身也可以被停牌/退市，逻辑完全相同

### 代码位置

| 关注点 | 位置 |
|---|---|
| 下单时的单标的校验 | `tradingService.assertStockTradable` |
| 退市批量撤单解冻 | `tradingService.cancelAllPendingOrders` |
| 撮合时跳过非正常标的 | `cycleJob.tick`（只对 status=1 调 `settleAll`） |
| 定价时跳过退市标的 | `cycleJob.recomputeAll`（过滤 status=2） |
| 管理端设置状态 / 改代码 | `adminController.updateStock` |
| 公开列表隐藏退市 | `stockController.list`（`status != 2`） |

### 超级管理员改代码

- 仅 `role='root'` 可改，普通 admin 提交会收到 403
- 服务端统一转大写，只允许 `A-Z 0-9 _ -`，长度 2~16
- **提交前查重**：与其它标的重复直接返回 409 并指明占用者，**不会写库**
- 名称同样做了查重（原来只有数据库唯一约束兜底，错误信息不友好）

## 10. 排查手册

**基金价格不动？**
1. `fund_enabled` 是否为 1
2. 基金是否配了成分股（没配时 NAV 退化为自身价格，只在有情绪时微动）
3. 是否刚好在两次结算之间（默认 10 分钟一轮，看 `/api/meta` 的 `cycleMinutes`）

**成分股没被拉动？**
1. 该周期基金是否真有净买入（成交量口径：买卖双边各计一次）
2. `fund_influence_weight` 是否被调成 0
3. 传导量级本就小：3 只等权成分股、压力打满也只有 +0.167%/周期

**K 线写不进去 / 结算报错？**
- 检查 `price_history.period` 是否为 `VARCHAR`（历史版本曾是 `ENUM('10m','1d')`，
  撮合周期改成非 10 分钟时会写入失败并回滚整轮结算）

**想看一轮结算到底算了什么？**
- 日志里每个标的都有一行 `[周期]`，形如：
  ```
  [周期] TC1xxx 某角色: 1000 → 1001.6667 (买0/卖0 压力0 新闻0 投票0 基金传导0.3333)
  [周期] TF1xxx 某基金(基金): 1000 → 1025.875 (净值1001.6667 溢价0.05 压力1 新闻0 投票0)
  ```
- 运维/测试可用 `runCycleOnce()` 手动触发一轮结算

## 11. 交易税、流通股标定与限流（2026-09-12 新增）

### 11.1 卖方印花税（唯一的摩拉回收阀门）

```
税率   = STAMP_TAX_RATE（server/.env，默认 0.005 = 0.5%）
税额   = round(成交额 × 税率)          仅 SELL 收取，BUY 恒为 0
卖方到账 = 成交额 − 税额
```

- `trades.amount` 保持**市场口径**的成交额不变（成交量/成交额统计不受影响），税额单独存 `trades.fee`；
- 盈亏报表的现金流按「到账金额」计（`amount − fee`），历史成交 `fee=0` 即为真实情况，不做回填；
- 为什么必须有：在此之前全项目**零回收阀门**（无手续费、无税、无销毁），而注册送 100 万 + 交易盈亏
  让全服摩拉只增不减（实测 124 个账号共 1.10 亿摩拉），属结构性通胀。
- 代码位置：`services/tradingService.js` 的 `stampTaxCents()` / `executeSell()`。

### 11.2 流通股标定（total_shares 决定价格敏感度）

```
压力因子 = clamp(净买入股数 / total_shares × PRESSURE_GAIN(200))
涨跌幅   = 0.5(压力权重) × 压力因子 × 0.02(基础波动率) = 股数 × 2 / total_shares（压力未饱和时）
```

原标定为 500 万 / 800 万，而全服玩家资金仅约 1.1 亿摩拉（人均 ~89 万）：一个玩家把**全部身家**
（约 985 股）砸进一只股票，价格只动 **0.039%**；实测近 24 小时 128 只个股平均振幅 **0.0373%**，
121 只 < 0.05%（同期三只基金振幅 476%~721%）。个股市场实际上是死的。

现按「20 万摩拉（约 220 股）推动约 0.5%」重新标定，保留原有的相对次序：

| 原值 | 新值 | 含义 |
|---|---|---|
| 1,000,000 | 40,000 | 小盘（最妖） |
| 3,000,000 | 60,000 | |
| 5,000,000 | 80,000 | 主力档 |
| 8,000,000 | 120,000 | |
| 10,000,000 | 150,000 | |
| 50,000,000 | 200,000 | 大盘（最稳） |

> 该调整**不影响任何人的持仓股数与市值**（市值 = 股数 × 现价），只影响"交易对价格的推动力"
> 与展示用的流通市值/流通股数。迁移脚本 `server/sql/migrations/2026-09-12_total_shares_rescale.sql`
> 仅当库中还存在 ≥100 万的旧量级时才执行，可安全重复运行。

另注：个股四因子加权之和最大 1.25 → `×0.02 = ±2.5%/周期`，所以 `max_change=0.10` 对**个股**是
永远吃不到的死参数；只有基金（走 NAV 收敛，rawChange 可达数百 %）才会真的吃满 ±10%。

### 11.3 下单限流（两道闸门）

| 设置项 | 默认 | 作用 |
|---|---|---|
| `order_rate_per_min` | 12 | 每人每分钟下单上限（防脚本高频刷单 + 保护 2 核机器） |
| `order_rate_per_hour` | 180 | 每人每小时下单上限（压制挂机脚本长时间刷） |

- 令牌桶实现在 `middlewares/rateLimit.js`，`capacity` 支持传函数 → **控制面板改完即时生效**，无需重启；
- 0 表示关闭该闸门；撤单另有 `config.rateLimit.cancel`（默认 60/分钟）；
- 高频来回交易在本系统里**本来就赚不到钱**（同一周期内价格不变，每次往返再扣 0.5% 印花税），
  所以限流主要用于保护服务器与防刷单占位，而不是平衡经济。

### 11.4 排行榜（每周期算一次 + 内存快照）

- `services/rankService.js`：`rankDue()` / `refreshRankSnapshot()` / `getRankSnapshot()`；
- 由 `jobs/cycleJob.js` 的 P3.5 与 30 秒看门狗触发，按 `rank_interval_minutes` 节流；
- 前端每次刷新都读内存，**不碰数据库**；实测计算耗时 3ms（100 用户量级）；
- 只取前 50 名、只返回昵称与金额，尊重 `users.rank_opt_in` 开关。

## 12. 最少持有周期（T+N 锁仓）

### 12.1 规则

```
买入的份额必须持有满 X 个周期才能卖出          X = min_hold_cycles（控制面板，默认 3）
锁仓时长 = X × cycle_minutes                  （默认 3 × 10 分钟 = 30 分钟）
```

- **买入不受限**，只有卖出受限；
- 卖出时若所需份额里有任一部分**未满 X 个周期**，**整单拒绝**，接口返回 403 与固定文案：

  > 该份额持有周期过短，不得卖出。请在买入X个周期后卖出

  （X 为当前设置值；前端在委托面板做同样的预检，不会白跑一次请求。）
- 限价卖单在**挂单前**就被拦下（否则会挂上去、等到结算时才失败）；
- `min_hold_cycles = 0` 即关闭限制（此时买入立即可卖）。

### 12.2 为什么需要一张 holding_lots 表

`holdings` 是「用户 × 标的」一行、只有加权平均成本，**没有任何时间信息**，无法回答"这一股是什么时候买的"。
所以每次买入额外写一条批次（`holding_lots`）：`quantity` = 本次买入股数，`unlock_at` = 买入时刻 + 锁仓时长。
卖出按 **FIFO**（先买的先卖）消费批次，只允许消费 `unlock_at <= now` 的批次。

这样做的两个好处：
1. **只锁新买的部分**，不会因为"补仓 1 股"就把已经持有多日的老仓位重新冻住；
2. 分批买入各自计算解锁时间，与真实交易所的 T+N 语义一致。

### 12.3 三个容易踩的细节

1. **存量持仓宽限**：本功能上线前就存在的持仓没有批次记录 → 一律视为早已解锁。
   因此可卖数量的公式是：
   ```
   可卖 = (持仓总量 − 批次总量) + 已解锁批次量
   锁定 = 批次总量 − 已解锁批次量
   ```
   前一项即"无批次的历史持仓"，只有老仓位才会命中。
2. **关闭限制时也必须消费批次**：若关闭时跳过消费，批次会不断残留，
   下次开启限制时这些"幽灵批次"会把可卖池撑大（实测踩过这个坑：
   关着限制买卖一轮后再开启，新买入的股票居然能立刻卖出）。**始终 FIFO 消费**才能保证
   「批次总量 == 持仓量」这个不变式。
3. **锁仓时长在买入时固化**：`unlock_at` 写入时按当时的 `cycle_minutes` 折算，
   之后管理员改周期长度**不会**追溯改变已有批次的解锁时间。

### 12.4 接口与界面

- 持仓接口（`/user/holdings`、`/user/account`、`/user/trade/:id` 相关）新增三个字段：
  `lockedQuantity`（锁仓股数）、`sellableQuantity`（当前可卖）、`unlockAt`（下一批解锁时间）；
- `/api/meta` 公开 `minHoldCycles`，供「关于」页与委托面板展示；
- 委托面板：卖出时显示「可卖 X 股」+「🔒 另有 Y 股锁仓中，最早 HH:mm 解锁」，"最大"按钮按可卖数量填充；
- 「我的」持仓表：显示 `持仓 / 冻结 / 锁仓`，并给出可卖数量与解锁时间；
- 代码位置：`services/tradingService.js` 的 `minHoldCycles()` / `loadLockState()` / `consumeLots()` / `assertSellable()`。

### 12.5 排查

**刚买就能卖？**
1. `min_hold_cycles` 是否为 0（关闭状态）；
2. 该持仓是不是**本功能上线前的存量**（无批次 → 视为早已解锁，属预期）；
3. 查 `SELECT * FROM holding_lots WHERE user_id=? AND stock_id=?` 看批次是否存在、`unlock_at` 是否正确。

**该能卖却提示周期过短？**
1. 批次总量是否大于持仓总量（说明有历史残留批次）→ 属于脏数据，可按持仓量手工校正；
2. `created_at`/`unlock_at` 是否被手工改过；
3. 是否改了 `cycle_minutes` 后又买入（新批次的锁仓时长按新周期折算，属预期）。

## 13. 平仓盈亏（已实现盈亏）

### 13.1 口径

```
cost_amount     = round2(该笔成交时的移动加权均价 × 数量)        仅 SELL，BUY = 0
realized_profit = 成交额(amount) − 印花税(fee) − cost_amount      仅 SELL，BUY = 0
```

- **税后**净盈亏：印花税已经扣掉，与成交记录里的「实际到账」一致（`到账 = amount − fee`）；
- **移动加权平均成本**：与「我的 → 持仓」显示的成本价、浮动盈亏**同一口径**，所以两处数字对得上；
  （不采用 FIFO 批次成本，否则同一件事在两处会给出不同的数字，更容易让人困惑）
- **恒等式**：`Σ 已实现盈亏（所有卖出） + 持仓浮动盈亏（未实现） = 交易总盈亏`
  `/user/account` 直接返回 `realizedProfit` / `holdingProfit` / `tradingProfit` 三个字段。

### 13.2 为什么要存字段，而不是每次现算

现算需要把该用户的全部成交流水按时间序重放一遍；交易量一大会随页请求线性变慢
（1 万笔约 10~30ms/次，且每次都要多查一批流水）。存字段后：

- **写路径零额外查询**：`holding.avgCost` 本来就在撮合事务的内存对象里，
  只需 `cost = round2(avgCost × qty)`、`realized = net − cost` 两个乘减运算；
- **读路径零计算**：成交记录只是多返回两个字段（每行约 +50 字节）；
- **存储**：每行 +约 20 字节（`trades` 表当前 300+ 行 → 不到 10KB）。

### 13.3 历史数据回填

`deploy/backfill-realized-pnl.mjs

```bash
node deploy/backfill-realized-pnl.mjs --dry-run   # 只看结果与对账，不写库
node deploy/backfill-realized-pnl.mjs             # 真正回填
```

- 按 `(user_id, stock_id)` 时间序重放全部成交，用与后端完全一致的移动加权法
  （`avg = round4((oldQty×oldAvg + price×qty)/newQty)`，清仓后均价归零）；
- **幂等**：每次运行都从零重放，可重复执行；只 UPDATE `trades` 的这两列，不动金额；
- 结束时会用推演出的期末持仓与 `holdings` 表**对账**并打印不一致项；
- 实测（生产 328 条成交 / 88 个持仓）：**股数与成本价 88/88 完全一致，0 处不一致**。

**对账不一致意味着什么**：通常是「管理员删过成交记录」或「持仓被手工改过」，
这类账号的重放链条会断，回填结果只是近似值——需要时可按 `holdings.avg_cost` 手工校正。

### 13.4 界面

- 成交记录新增「平仓盈亏」列：卖出显示带色 `+/−`（副行给出该笔成本与收益率），买入显示 `—`；
- 「我的」页顶部新增「累计平仓盈亏（已实现）」与「交易总盈亏（= 已实现 + 未实现）」；
- 「关于」页说明了口径（含「已实现 vs 未实现」的区别）。

## 14. 市场情绪接入撮合（2026-09-14）

### 14.1 一句话口径

> **市场情绪 = 与「新闻」并列的一档独立因子**；审核只决定「能不能公开显示」，
> 由面板开关 `sentiment_before_review` 决定它「要不要先过审才能影响股价」。

用户的原始诉求：「让市场情绪和新闻因子一起影响股价；加一个开关，控制审核通过前要不要影响撮合价；
审核的目的只是不让没审过的文字直接公开到网站，不是不让它影响价格。」

### 14.2 开关语义（`sentiment_before_review`）

| 取值 | 参与定价的情绪行 | 前台展示 | 适用场景 |
|---|---|---|---|
| **开（默认）** | `PENDING` + `APPROVED` | 只有 `APPROVED` | 「审核=内容风控」：AI 写错话要拦住，但市场该有反应 |
| 关 | 只有 `APPROVED` | 只有 `APPROVED` | 与新闻完全同口径：管理员点头后价格才动 |

`REJECTED`（已驳回）**在任何取值下都不参与定价** —— 人工判定「这条总结是错的」，
就不该留下价格痕迹；这一点和新闻一致，也是审核权的实质内容。

实现位置：`engine.js → loadSentimentRows()`，一处判断同时管住角色股与基金（两条公式共用因子）。

### 14.3 权重为什么定为 0.2

| 因子 | 权重 | 单周期最大贡献（×0.02 基础波动率） | 理由 |
|---|---|---|---|
| 压力 wP | 0.5 | ±1.0% | 真金白银的买卖，最硬 |
| 新闻 wN | 0.3 | ±0.6% | 人工发布 + 有来源链接 + 有投票 |
| 投票 wV | 0.2 | ±0.4% | 操作员表态 |
| **情绪 wS** | **0.2** | **±0.4%** | 自动抓取、噪声比人工新闻大，所以给新闻的 2/3 |
| 基金传导 wI | 0.25 | ±0.5% | 一期已有 |

- 不给到 0.3（=新闻）：AI 总结的社区讨论里「情绪浓度」天然偏高，与人工新闻同权容易把价格推成情绪盘；
- 不给到 0.1 以下：低于「操作员投一票」就没人会注意到它，等于白抓；
- **可关停**：置 0 则情绪只展示不影响股价，无需改代码、无需重启（面板改完下一轮生效）。

### 14.4 验收记录（本地实测，2026-09-14）

### 14.5 「抓回帖」的真实开销（2026-09-14 实测，服务器 701MB 内存 / NGA 生产网络）

> **结论先说：回帖不花额外的请求，一分钱网络成本都没有 ——
> 因为主楼和回帖本来就在同一个 HTML 里；真正的开销只有「送进 AI 的字数变多」。**

实测数据（fid=650,835 各取 12 帖）：

| 指标 | 只看标题 | 1 层（修复前的实际行为） | 8 层（当前线上） | 20 层（整页） |
|---|---|---|---|---|
| HTTP 请求 | 12 | 12 | **12（完全相同）** | 12 |
| 下载字节（明文） | 0 | 419KB | **419KB（完全相同）** | 419KB |
| 下载字节（gzip 后・当前） | 0 | ≈116KB | **≈116KB（完全相同）** | ≈116KB |
| 抓取耗时 | 0 | 3.55s | **3.55s（完全相同）** | 3.55s |
| 提示词字数 | 874 | 1696 | 5854 | 12923 |
| 提示词 tokens | 607 | 1248 | 4259 | 9383 |
| Gemini 时延 | — | 2.48s | 2.83s（+0.35s） | 约 +1s（线性外推） |
| 内存增量 | 0 | ≈0.8KB | ≈4.7KB | ≈12KB |

- **每帖一次请求、明文约 35KB（gzip 后约 10KB）、0.30s**：这一份 HTML 里就有主楼 + 约 19 层回复（第 1 页）；
  取 1 层还是 20 层，请求数与下载量**完全一样**，区别只在正则摘多少字进提示词；
  （两个 NGA 接口的完整字段表、gzip 协商、JSON 版对比见 **`docs/NGA_API.md`**）
- **gzip 是 2026-09-14 开的**（`Accept-Encoding: gzip, deflate`）：实测正文页 41.3KB → 12.8KB（省 69%），
  列表 21.8KB → 约 6KB，`_open()` 自动解压。顺带说明：这也正是**不值得为省字节改用 JSON 版**的原因
  （JSON 只省 65%，却要承担 17% 的 CDN 截断率）；
- 第 2 页（第 21 楼往后）才需要额外请求：约 **44KB / 0.27s / 16 层**，可以在需要时再加；
- 进程峰值内存实测 **34.8MB**（`rlimit AS` 上限 64MB）；正文只保留「每层 240 字」的纯文本，
  原始 HTML 摘完立刻释放、不落临时文件，所以层数几乎不影响内存；
- 时间构成：一期 12 帖正文抓取 3.55s + 两次 Gemini 调用（分析 2.8s + 总结 2.5s）≈ **9s/轮**，
  而 `nga_interval_minutes` 默认 180 分钟才真跑一轮 → 平均 CPU 占用可忽略。

**成本量级**：8 层比 1 层多约 3000 输入 tokens/轮；按 180 分钟一轮 = 8 轮/天，
多 2.4 万 tokens/天 ≈ 按 flash-lite 单价折算 **每天不到 1 分钱**。
真正的取舍是**分析质量 vs 提示词长度**，不是钱。

### 14.6 顺手修掉的 bug：回帖其实一直没被抓到

同一份 HTML 里主楼写的是 `<p id='postcontent0' class='postcontent ubbcode'>…</p>`，
而**回复楼层写的是 `<span id='postcontent1' class='postcontent ubbcode'>…</span>`**。
旧正则把结束标签写死成 `</p>`：

```python
# 旧（只能匹配主楼）
r"id='postcontent\d*'[^>]*class='[^']*ubbcode[^']*'[^>]*>(.*?)</p>"
# 新（同标签名开闭配对 + 属性顺序无关）
r"<(p|span|div|td)\b(?=[^>]*id='postcontent\d*')(?=[^>]*class='[^']*ubbcode)[^>]*>(.*?)</\1>"
```

实测一页明明有 **20 层**，旧正则只摘出 **1 层**（主楼），也就是说
「抓正文/抓回帖」这项能力上线以来**从未真正生效**，日志里的 `正文=11/13帖` 只代表
「11 个帖子抓到了主楼」，跟回帖无关。修复后同一页能摘出 20 层，
在不增加任何请求的前提下把送进 AI 的社区讨论量提高约 3.4 倍（1248 → 4259 tokens）。

回归断言见 `server/scripts/_selftest_nga_analysis.py` 的「4b. 楼层解析」段（7 条）；
楼层 HTML 结构、正则写法与两个接口的完整字段表见 **`docs/NGA_API.md`**。
